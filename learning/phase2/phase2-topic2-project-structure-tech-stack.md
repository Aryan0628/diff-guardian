## Part B: Import Dependency Graph

Understanding who imports whom reveals the **layering discipline** of the project:

```
                    ┌──────────┐
                    │  cli.ts  │  ← entry point (top of the stack)
                    └────┬─────┘
                         │
                    ┌────▼──────┐
                    │pipeline.ts│  ← orchestrator (imports everything)
                    └────┬──────┘
                         │
         ┌───────────────┼───────────────┬─────────────────┐
         ▼               ▼               ▼                 ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐     ┌──────────┐
   │ git-diff │   │ast-mapper│   │classifier│     │  tracer   │
   │  .ts     │   │  .ts     │   │ engine   │     │ scanner  │
   └────┬─────┘   └────┬─────┘   └────┬─────┘     │ tracer   │
        │              │              │           └────┬─────┘
        │         ┌────▼─────┐   ┌────▼─────┐         │
        │         │translators│  │  rules/  │    ┌────▼──────┐
        │         │ ts,py,go │  │ R01..R28 │    │ languages │
        │         │ java,rust│  └────┬─────┘    │ ts,py,go  │
        │         └────┬─────┘       │          │ java,rust │
        │              │             │          └────┬──────┘
        ▼              ▼             ▼               ▼
   ┌─────────────────────────────────────────────────────┐
   │                  core/                               │
   │    types.ts   constants.ts   utils.ts               │
   └─────────────────────────────────────────────────────┘
   ← foundation layer (imported by everyone, imports nothing from src/)
```

**Key rules:**
1. **`core/` imports nothing from `src/`** — it's the foundation layer
2. **`pipeline.ts` imports from every module** — it's the orchestrator
3. **Modules don't import each other sideways** — `classifier` doesn't import from `tracer`, `parsers` doesn't import from `reporter`
4. **Each module only depends downward** — toward `core/`

This is the **Layered Architecture** pattern. It makes the code testable (you can test the classifier without the tracer), maintainable (changes in one module don't cascade), and understandable (clear boundaries).

## Part C: The Two Entry Points

The project has **two entry points** — one for CLI users, one for library consumers:

### Entry Point 1: CLI — `cli.ts`

```
npx dg compare main feature-branch
       │
       ▼
  cli.ts (shebang: #!/usr/bin/env node)
       │
       ├── parses args with minimist
       ├── determines command: 'compare'
       ├── resolves git refs
       └── calls runPipeline(opts)
```

When you run `npx dg`, Node.js executes `dist/cli.js` (compiled from `src/cli.ts`). The `bin` field in `package.json` maps `dg` to this file:

```json
"bin": {
  "diff-guardian": "./dist/cli.js",
  "dg": "./dist/cli.js"
}
```

### Entry Point 2: Library API — `index.ts`

```typescript
// Some other tool using Diff-Guardian programmatically
import { runPipeline, ClassifierEngine, ASTMapper } from 'diff-guardian';

const exitCode = await runPipeline({
  baseSha: 'main',
  headSha: 'HEAD',
  config: { mode: 'strict', format: 'json' },
});
```

The `main` field in `package.json` points to `dist/index.js`:

```json
"main": "dist/index.js",
"types": "dist/index.d.ts"
```

[index.ts](file:///Users/aryangupta/Documents/Projects/diff-guardian/src/index.ts) re-exports only what external consumers need — the pipeline, engine, mapper, and core types. Internal modules like `cli.ts`, `terminal.ts`, and individual rules are NOT exported.

### Alternatives Considered

| Category | Chosen | Alternative | Why not |
|----------|--------|------------|---------|
| **Language** | TypeScript | JavaScript, Rust, Go | TypeScript for type safety + ecosystem familiarity. Rust/Go would be faster but harder for contributors. |
| **Parser** | Tree-Sitter (WASM) | Babel, SWC, ANTLR | Only Tree-Sitter handles 6+ languages through one API with WASM portability. |
| **CLI framework** | minimist | Commander, Yargs, oclif | Minimist is ~1KB with zero deps. Commander/Yargs are 100KB+. For 5 commands, minimist is plenty. |
| **Colors** | chalk v4 | chalk v5, kleur, picocolors | chalk v4 is CommonJS (our project uses `"module": "commonjs"`). v5 is ESM-only — would need config changes. |
| **Test runner** | Vitest | Jest, Mocha, Ava | Vitest has native TypeScript support, no Babel config needed. Jest requires ts-jest or babel setup. |
| **Hooks** | Husky | simple-git-hooks, lefthook | Husky is the de facto standard, most developers already know it. |

## Part E: `package.json` Deep Dive

```json
{
  "name": "diff-guardian",
  "version": "0.1.3",
```

**`version: 0.1.3`** — Pre-1.0, semver says anything goes. The project is in active development.

```json
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
```

**`main`** — What `require('diff-guardian')` resolves to. Points to compiled JS.
**`types`** — TypeScript declaration file. So library consumers get autocomplete and type checking.

```json
  "files": ["dist/", "grammars/", "README.md", "LICENSE"],
```

**`files`** — What gets published to npm. Only `dist/` (compiled code), `grammars/` (WASM binaries), and docs. Source code (`src/`), tests, dev configs are NOT shipped.

```json
  "engines": { "node": ">=18" },
```

**`engines`** — Requires Node.js 18+ because of WASM support, `structuredClone`, and ES2020 features.

```json
  "bin": {
    "diff-guardian": "./dist/cli.js",
    "dg": "./dist/cli.js"
  },
```

**`bin`** — Registers two CLI commands: `diff-guardian` (full name) and `dg` (shorthand). Both point to the same file. When you run `npx dg`, npm creates a symlink to this file.

```json
  "scripts": {
    "prepare": "husky",
    "build": "tsc",
    "postbuild": "chmod +x dist/cli.js",
    "build:grammars": "mkdir -p grammars && npx tree-sitter build --wasm ... && mv *.wasm ./grammars/",
    "dev": "tsx src/index.ts",
    "test": "vitest",
    "lint": "tsc --noEmit"
  },
```

| Script | What it does |
|--------|-------------|
| `prepare` | Runs after `npm install` — sets up Husky git hooks automatically |
| `build` | Compiles TypeScript to JavaScript using `tsc` |
| `postbuild` | Makes `dist/cli.js` executable (Unix `chmod +x`) — needed for shebang to work |
| `build:grammars` | Downloads and compiles all 6 Tree-Sitter grammars to WASM binaries |
| `dev` | Runs source TypeScript directly using `tsx` (no compile step) |
| `test` | Runs test suite with Vitest |
| `lint` | Type-checks without emitting — catches type errors without producing output |

### `tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "ES2020",          // Output JS uses ES2020 features (optional chaining, etc.)
    "module": "commonjs",        // CommonJS modules (require/module.exports)
    "outDir": "./dist",          // Compiled output goes here
    "rootDir": "./src",          // Source files root
    "strict": true,              // All strict checks enabled
    "declaration": true,         // Generate .d.ts files for library consumers
    "esModuleInterop": true      // Allow default imports from CJS modules
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist", "tests/fixtures"]
}
```

**Why CommonJS (`"module": "commonjs"`):**
- chalk v4 is CommonJS
- `__dirname` is needed for WASM grammar resolution (ESM uses `import.meta.url` instead)
- Most Node.js CLI tools still use CommonJS for broadest compatibility

**Why ES2020 target:**
- Requires Node.js 18+ anyway (for WASM)
- Gets optional chaining (`?.`), nullish coalescing (`??`), `Promise.allSettled()`

## Part F: The `files` Field — What Gets Shipped

When someone runs `npm install diff-guardian`, they get **only** what's in `"files"`:

```
node_modules/diff-guardian/
├── dist/              ← Compiled JS + type declarations
│   ├── cli.js         ← The CLI binary
│   ├── index.js       ← Library entry point
│   ├── index.d.ts     ← TypeScript types
│   ├── pipeline.js
│   ├── core/
│   ├── parsers/
│   ├── classifier/
│   ├── reporter/
│   └── tracer/
├── grammars/          ← Pre-built WASM binaries (6 files)
├── README.md
└── LICENSE
```

They do NOT get:
- `src/` (TypeScript source — unnecessary, they have compiled JS)
- `tests/` (test code)
- `learning/` (study materials)
- `.husky/` (git hooks — those are for contributors, not users)
- `.github/` (CI config)

This keeps the npm package small (~5MB, mostly WASM binaries).

## Key Terms

| Term | Definition |
|------|-----------|
| **Barrel file** | An `index.ts` that re-exports from child modules (e.g., `export { X } from './x'`) |
| **Shebang** | `#!/usr/bin/env node` at the top of `cli.ts` — tells the OS to run with Node.js |
| **`bin` field** | In `package.json` — registers CLI commands that npm makes globally available |
| **`main` field** | In `package.json` — what `require('package-name')` resolves to |
| **`files` field** | In `package.json` — whitelist of files included in the npm tarball |
| **Layered architecture** | Design where each layer only depends on layers below it, never sideways or upward |
| **CommonJS** | Node.js module system using `require()` and `module.exports` |
| **ESM** | ECMAScript Modules using `import`/`export` — the modern standard |

## 🎤 Interview Q&A

### "Walk me through the project structure"

> "The project follows a layered architecture with clear boundaries. At the bottom is `core/` — shared types, constants, and utilities that everything depends on. Above that are four domain modules: `parsers/` for source extraction and AST parsing, `classifier/` for rule-based change detection, `tracer/` for call-site blast radius analysis, and `reporter/` for output rendering. At the top is `pipeline.ts` which orchestrates all modules, and `cli.ts` which handles user interaction. Each layer only imports downward — the classifier doesn't know about the tracer, the tracer doesn't know about the reporter."

### "Why TypeScript over JavaScript?"

> "Type safety. The project passes complex data structures between 6 pipeline phases — `FileDiff`, `ParseResult`, `FunctionChange`, `CallSite`, `AnalysisResult`. Without types, it would be extremely easy to pass the wrong shape and only discover it at runtime. TypeScript catches those at compile time. It also gives library consumers autocomplete and type checking through the `.d.ts` files we ship."

### "Why minimist instead of Commander or Yargs?"

> "We have exactly 5 commands with simple argument patterns. minimist is ~1KB with zero dependencies. Commander is 100KB+ and Yargs is even larger. For our use case, there's no benefit to the extra weight — we don't need auto-generated help pages, subcommand classes, or prompt systems. We wrote help text manually in about 30 lines. The engineering principle: use the smallest tool that solves the problem."

### "Why is chalk pinned to v4?"

> "chalk v5 switched to ESM-only modules. Our project uses CommonJS (`\"module\": \"commonjs\"` in `tsconfig.json`) because we need `__dirname` for resolving WASM grammar paths, and most of the Node.js ecosystem still expects CommonJS for CLI tools. chalk v4 is the last version that exports CommonJS. It's a pragmatic trade-off — v5 doesn't add any features we need."

### "What does the `prepare` script do?"

> "`prepare` is a special npm lifecycle hook that runs automatically after `npm install`. Ours runs `husky`, which installs git hooks — `pre-push`, `pre-merge-commit`, and `post-merge` — into the `.git/hooks` directory. This means any contributor who clones and installs automatically gets the hooks without any manual setup. It's zero-friction enforcement."
